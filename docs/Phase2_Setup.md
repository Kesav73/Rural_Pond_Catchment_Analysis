# Installation and running — Phase 2

## Deployed instance

**`http://10.1.75.53:4282`**

```bash
curl -X POST http://10.1.75.53:4282/api/analyzeContour \
     -F "file=@backend/data/contours_1m.kml"
```

Interactive docs: <http://10.1.75.53:4282/docs>

Runs in a container reachable only on the institute network. Port 4000 inside maps to 4282
outside; 3282/4282/5282/6282/7282 map to 3000/4000/5000/6000/7000 respectively, and 3000 was
already taken. Managed by `~/start_api.sh` (start or restart) and `~/supervise.sh` (restarts
uvicorn if it dies). There is no cron or systemd in the container, so **the API does not come back
automatically after a container restart** — re-run `bash ~/start_api.sh` over SSH.

### Container limits worth knowing

The container is capped at **512 MB memory and 1 CPU**. Note that `free` and `nproc` inside it
report the *host's* hardware (128 GB, 120 CPUs) and are misleading; the real limits are in
`/sys/fs/cgroup/memory.max` and `/sys/fs/cgroup/cpu.max`.

The sample map peaks at ~382 MB, which fits — but only after `flow_accumulation` was changed to
keep numpy arrays instead of Python lists. The list version cost 158 MB more and was OOM-killed
here. A substantially larger contour map may still exceed the limit; pass a coarser `resolution_m`
if so.


## Requirements

- Python 3.12
- A PostgreSQL connection string (the project uses a hosted Neon database). It caches elevation
  tiles, satellite land-cover images and rainfall series so repeat requests do not re-download them.

## Setup

```bash
cd backend
python3.12 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt

cp .env.example .env      # then set DATABASE_URL
```

## Run

```bash
cd backend
source .venv/bin/activate
uvicorn app.main:app --port 8000
```

Check it is alive:

```bash
curl http://127.0.0.1:8000/api/health      # {"status":"ok"}
curl http://127.0.0.1:8000/api/health/db   # {"status":"ok"}
```

Interactive API docs (auto-generated by FastAPI): <http://127.0.0.1:8000/docs>

## Analyse a contour map

```bash
curl -X POST http://127.0.0.1:8000/api/analyzeContour \
     -F "file=@backend/data/contours_1m.kml"
```

Takes about 30 seconds on the provided sample. Most of that is the terrain computation on a
1.36-million-cell grid plus the satellite water lookups; there is no artificial delay.

Optional parameters:

```bash
curl -X POST "http://127.0.0.1:8000/api/analyzeContour?resolution_m=5&top_n=3" \
     -F "file=@my_survey.kmz"
```

## Tests

```bash
cd backend
source .venv/bin/activate

pytest                      # everything
pytest -m "not slow"        # skips network + full-pipeline tests (a few seconds)
```

`slow` marks the tests that fetch satellite imagery and rainfall or run the whole pipeline. The rest
are pure parsing and geometry and need no network.

## Independent water-exclusion check

Confirms that no proposed pond sits on existing water, by re-fetching the satellite mask rather than
trusting the endpoint's own report. Needs the server running.

```bash
cd backend
.venv/bin/python scripts/verify_water_exclusion.py data/contours_1m.kml
```

## Visual check of the water screening

Renders satellite imagery beside the computed water mask and the proposed sites. Needs the server
running.

```bash
cd backend
.venv/bin/python scripts/render_water_check.py data/contours_1m.kml
```

Writes `data/water_exclusion_check.png`. Unlike `verify_water_exclusion.py`, this compares the mask
against an independent source (imagery) rather than against itself.

## Layout

```
backend/app/
  routers/analyze_contour.py   POST /api/analyzeContour — the Phase 2 deliverable
  services/kml.py              KML/KMZ parsing -> contour lines + boundary
  services/surface.py          contour lines -> elevation grid (TIN interpolation)
  services/gridref.py          georeferencing seam: tile-based and lon/lat grids
  services/terrain.py          Priority-Flood, D8, flow accumulation, catchment delineation
  services/worldcover.py       satellite water mask (land cover + shortwave infrared)
  services/water_exclusion.py  screens candidates against existing water
  services/pond_sizing.py      Rational Method runoff, capacity, capture
backend/scripts/               verification scripts (water exclusion, visual check)
backend/tests/                 pytest suite; fixtures.py builds synthetic contour maps
backend/data/contours_1m.kml   the provided sample
docs/Phase2_API.md             endpoint reference, method, extensibility, limitations
docs/Phase2_Demonstration.md   worked example against the sample
```

## Note on external services

The endpoint calls three outside services: AWS Terrain Tiles (only for the cross-validation script),
ESA WorldCover via Terrascope (satellite water), Open-Meteo (rainfall), and Overpass/OpenStreetMap
(mapped water, optional). All are keyless.

Each degrades rather than failing the request, and the response reports which ones answered —
`screening.worldcover_available`, `swir_available`, `osm_available`, and `source.rainfall_available`.
A `false` there means that particular check did not run, and the result is a reduced screen rather
than a complete one.
